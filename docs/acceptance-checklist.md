# 验收清单：十项可当场验证的验收

> 用途：这份单子不是"功能清单"，是**验收标准**。每一项都写清"怎么验、合格长什么样、不过说明哪里坏了"。
> 交付或发版前全跑一遍；也可以只挑 3 条验证、其余按需说明。全跑一遍约 15 分钟。

## 用法

| 场景 | 怎么做 |
| --- | --- |
| 发版前 | 跑一次全套：材料回归 + 题库评测 + 账本验收（见下面每项的"怎么验"） |
| 开始前 2 分钟 | `.venv\Scripts\python.exe scripts\demo_check.py`（全 OK 再继续） |
| 演示时 | 优先跑 ✅ 标记的三条（越界、解析失败、批准卡），其余按需说明并指向屏幕 |

标记含义：✅ 现在就能验 · ⚠️ 能验但要先做准备（改配置/重启） · 🕐 还没做（如实标注，不要假装已完成）

---

## 心 · 证据与边界

### 1. 每条结论都能点回原文 ✅

**怎么验**：跑一次 `.venv\Scripts\python.exe scripts\regression_check.py`，看分数表里"非待补依据的结论都有证据""证据都能落到页码"两项；现场再随便挑一条判断，展开"判断依据"逐条点开。

**合格**：每条依据都能落到客户材料或企业能力库的真实页码上，点开能看到那段原文。

**不过说明**：证据落库或响应映射坏了 —— 结论和页码对不上，是这个产品最不能坏的器官。

**一句话**：每条结论都能点回原文，要么是客户材料，要么是我们自己的产品文档。

### 2. 结论不越界（红线）✅

**怎么验**：

```bash
$env:FITWISE_SANDBOX_PORT="8023"; .venv\Scripts\python.exe scripts\regression_check.py --testset
# 或只跑这一份
$env:FITWISE_BASE="http://127.0.0.1:8023"; .venv\Scripts\python.exe scripts\check_testset.py --only 05
```

**合格**：分数表里"05 越界率 = 0"，且"A0 大幅面图纸"被判**暂不支持**。

**不过说明**：规则层的结论上限被绕过了 —— AI 说了知识库里没有的能力。

**一句话**：我们做不了的，它会明确说做不了。这条是服务端规则给的硬上限，不是提示词里求它听话。

### 3. 没有证据就不下结论 ✅

**怎么验**：找一条判"待补依据"的（例如"档案数据不得留存或用于训练"），看它的理由和自检结果。

**合格**：没有任何支持类证据、结论上限就是"待补依据"，而且**不会编一个页码出来**。

**不过说明**：自检失效 —— 模型开始替人做承诺。

**一句话**：知识库里没有依据的，它只会说"待补依据"，不会顺着客户的话往下承诺。

## 肝 · 意外输入与兜底

### 4. 模型挂了仍然出结论，且标注清楚 ⚠️

**怎么验**：在沙箱实例上把 `LLM_API_KEY` 改错（或清空）后重启，重跑一条能力判断。

**合格**：仍然产出结论，界面上标注"本次为规则结果"，系统不报错、不空白。

**不过说明**：兜底路径坏了 —— 模型一抖，整个产品就不可用。

**注意**：在沙箱里验证，别在演示实例上动 `.env`；验完记得改回来。

**一句话**：模型服务挂了我们仍然有结论，只是会明确标注"这是规则兜底"，不装成模型输出。

### 5. 解析失败要说清原因 ✅

**怎么验**：上传 `scripts/testset/06-损坏文件.pdf`，或 `check_testset.py --only 06`。

**合格**：材料状态是"读取失败"，原因是 `[content] PDFError: The file is corrupted.` —— 带成因码，不出现"已读完但内容是空的"。

**不过说明**：静默失败 —— 最危险的一种坏法，用户以为读到了，其实什么都没读进来。

**一句话**：读不出来会说清楚为什么读不出来，不会给你一份看起来成功的空结果。

### 6. 人工改过的东西不会被重跑覆盖 ✅

**怎么验**：

```bash
# 确定性检查：临时库 + 假模型，验"重跑不冲掉人工修改"
.venv\Scripts\python.exe scripts\check_requirement_edits.py
```

现场版：改一条需求的标题或描述 → 对 Agent 说"重新跑一遍分析" → 等它跑完。

**合格**：改过的那条还在，带"已人工修改"标记；待确认问题只增不丢。

**不过说明**：重跑会把人的工作冲掉 —— 用过一次就不敢再用了。

**一句话**：AI 重跑不会把人改过的内容冲掉，人的修改优先级最高。

## 脑 · 决定权在谁手里

### 7. 该人点头的地方必须停下来 ✅

**怎么验**：对 Agent 说"帮我确认这些需求"。

**合格**：出现待批准卡；批准之后才开始能力判断；留痕由服务端写（谁、什么时候、批还是拒）。直接调接口也拿不到"基于草稿的结论"。

**不过说明**：人闸门只做在界面上，服务端没拦住 —— 这是权限问题，不是交互问题。

**一句话**：AI 只准备，人做承诺。这个闸门装在服务端，不是界面上把按钮藏起来了。

---

## 肺 · 能不能换

### 8. 换模型、换知识库不用改代码 ⚠️

**怎么验**：改 `LLM_BASE_URL` 指向另一个兼容端点（或本地模型）后重启，链路照跑；界面上如实标注数据流向。

**合格**：只改配置项，不动一行代码；界面上写明"材料会发往哪个端点"。

**不过说明**：模型被写死在代码里 —— 客户一提"数据不出内网"就答不上来。

**注意**：演示环境需要有一个可用的备用端点；没有就以界面上的数据流向标注为准。

**一句话**：换模型只改一个配置项。客户要求数据不出内网时，我们换成内网模型就行。

## 神经 · 看得见

### 9. 每次运行都能复盘 ✅

**怎么验**：

```bash
# 按项目看花了多少：调用次数、token、失败、回退、按步骤分组
GET /api/projects/{id}/ai-calls
# 按一次运行看完整链路（解析 → 抽取 → 每条判断 → 建议）
GET /api/traces/{trace_id}
```

**合格**：能当场说出"这次运行调了几次模型、多少 token、哪一步失败过、用的是哪版提示词"。

**不过说明**：只有日志没有账本 —— 出问题只能猜，出不了"为什么"。

**一句话**：每一次运行都有记录，能定位到具体哪一步、哪一版提示词，而不是只知道"结果不对"。

---

## 免疫 · 回得去

### 10. 改坏了能退回，改动有考试 ⚠️

**怎么验**：

```bash
git log --oneline            # 有基线提交，可回退
.venv\Scripts\python.exe scripts\regression_check.py --testset   # 每次改动的全量考试
```

**合格**：能退回上一版；每次改动后有一张分数表（端到端 10 项 + 对话审批 5 项 + 调用账本 9 项 + 题库 31 项）。

**现状**：分数表已经有了；"和上一版自动对比"还差一层（目前是看分数、人工比对，自动 diff 在计划里）。

**不过说明**：只能靠"我觉得没坏"迭代 —— 这正是要避免的那种开发方式。

**一句话**：每一版都能回退，每改一次都会跑一次全量考试，改坏了当场能看见。

## 尚未实现的能力与现状说明

| 能力 | 现状说明 |
| --- | --- |
| 出向 MCP、插件市场 | 不做。工具和能力库都在同一个库里，接 MCP 只增加故障面；等能力数据分散到多个系统再谈。 |
| 指标看板 | 数据都在库里（谁确认了哪条需求、谁覆写了哪条判断、每次调用花了多少），缺的是一个汇总页面；阈值还没定，得先由产品定。 |
| 自动对比上一版 | 分数表有了，自动 diff 还在补。 |
| 熔断、多活、灰度 | 不做。单机内网部署、三个内部用户、一个场景，做了不会让结论更可信。 |
| 真实用户验收数据 | 结构和留痕都齐了，还没有真实用户量；补法是六个前端事件埋点 + 一份真实公开招标文件进题库。 |
