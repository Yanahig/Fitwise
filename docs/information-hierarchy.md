# 界面信息层级：诊断与精简清单

> 结论：Fitwise 的问题不是「功能太多」，而是**同一个结论被说三遍、产品在向用户解释自己**。
> 功能一个没删，把所有「解释性、重复性、装饰性」的文字从常驻版面移到需要时才出现的层（`?` 气泡、`···` 菜单、折叠区），页面自然就像正经产品了。

---

## 1. 诊断：多余信息只有三类

| 类型 | 特征 | 例子（改动前） | 处理 |
| --- | --- | --- | --- |
| **重复信息** | 同一个结论在页面里出现 2–3 次 | 需求页：顶部「3 条已确认 · 5 条待确认」+ 标题下「共 8 项 · 已确认 3 · AI 推断 5 · 依据 2 份材料」+ 侧栏卡片「需求 3 · 匹配 8 · 缺口 2」 | 每处只留一份，其余删除 |
| **解释性信息** | 产品在解释自己为什么这么设计 | 「材料里明确写着的事实：背景、范围、工期、环境约束、时间点、决策链。每条可点回原文」 | 移入 `?` 气泡 / 折叠区 |
| **装饰性信息** | 有数字但不改变下一步动作 | 首页「进行中项目 3 / 能力文档与案例 14 / 待确认结论 2」、材料行「贡献 4 条需求」、判断置信度 % | 删除，或降级为 title 悬停提示 |

判断标准：

1. **这句话会改变用户的下一步动作吗？** 不会 → 不常驻。
2. **这个信息在本页别处出现过吗？** 出现过 → 只留信息量最大的那一处。
3. **这是「没有问题」的陈述吗？** 是（如「没有读取失败的材料」）→ 删掉，只在异常时说话。

---

## 2. 参照的 Apple 原则 → 落到具体做法

| 原则 | Fitwise 的具体做法 |
| --- | --- |
| 一屏一焦点 | 每个页面只有一个主按钮（上传材料 / 全部确认 / 复制建议），其余动作降为文字链或 `···` |
| 内容优先于框架 | 页头不再重复导航名与反问句（「客户给了什么」「客户到底要什么」全部去掉），改用一行状态：`1 份 · 3 页 · 全部已读取` |
| 需要时才出现（Progressive disclosure） | `?` 气泡放定义与口径；`···` 放低频操作（重新提取、删除、重新读取）；依据链默认折叠 |
| 用名词说话 | 标题改回名词：客户材料 / 客户需求；动作写在按钮上（上传材料），不再用疑问句当标题 |
| 安静即专业 | 正常状态不报「一切正常」，只报异常（`2 份读取失败`）；没有缺口时不出现「无缺口」标签 |
| 数字要能行动 | 保留能驱动决策的两个数（能力匹配度、赢单可能性），删掉过程指标（判断置信度、匹配度碎片） |
| 层级靠留白与字重 | 页面大标题只保留一个（售前建议的结论），模块标题降一档（`--text-xl`），信息行用 13px 灰字 |

## 4. 保留原则：什么必须有证据、必须常驻

精简不等于少给信息。以下内容**故意保留在版面上**，因为它们是 Fitwise 的信任基础：

- 每条结论的来源页码按钮（`第 3 页`）——证据可点回原文；
- 项目栏三个模块的数量徽标（1 / 11 / 10）——用户随时知道自己在第几步；
- 「还差什么」中最关键的信息缺口——它决定要不要马上问客户；
- 承诺边界与不可承诺清单——这是售前最需要背下来的内容。

## 5. 后续可以继续做的（未在本轮实施）

1. **文案预算**：每屏常驻说明文字 ≤ 1 句；同一事实全站只出现一次。新加文案时先问「删除哪一句」。
2. **数字可解释**：匹配度、赢单可能性点击后展开口径（现在是 `?` 说明，可升级为算式）。
3. **空状态统一**：全部改成一句动作句（做什么 → 会得到什么），不再出现解释性从句。

## 6. 第二轮：删提示 + 修「信息被折叠」（2026-09-13）

### 6.1 又删掉的两条常驻提示

| 位置 | 删除内容 | 理由 |
| --- | --- | --- |
| 工作台顶栏副标题 | 「今天该推进什么」 | 顶栏只需要说「你在哪」，标题「工作台」已经够了 |

同时移除了已无人使用的 `subtitle` 属性和对应样式。

### 6.2 修掉 4 处「信息被折叠」

用浏览器逐个页面扫描「内容溢出但被 overflow 裁掉」的元素后发现：

| 问题 | 影响 | 修法 |
| --- | --- | --- |
| `.req-item__detail` 用 `-webkit-line-clamp: 2` | 需求描述被砍成 2 行（7 条需求少了一多半内容） | 去掉行数限制，完整展示 |
| `.node-list p` 用 `-webkit-line-clamp: 2` | 项目信息 → 项目时间线每条约 4 行只显示 2 行 | 去掉限制，并把字号从 11px 提到 12px |
| 需求来源按钮 `document_name.slice(0, 18) + '…'` | 文件名被截成「…R…」 | 去掉截断：单份材料时只显示「第 N 页」，多份材料时显示完整文件名 + 页码（鼠标悬停也有全名） |
| 首页「已选择 N 份材料：…」`slice(0, 60)` | 选中的文件名列表被截断 | 去掉截断，全部列出 |

### 6.3 顺手修的展示细节

| 项目 | 改动前 | 改动后 |
| --- | --- | --- |
| 小字说明文字对比度 | 灰阶 `#8794a5`，对白底约 2.85:1（低于无障碍 4.5:1） | `#68727f`，约 4.5:1；`.hint` 字号 11px → 12px |
| 文字链与「···」菜单点击区 | 15–22px 高，不易点中 | 一律 ≥ 24px（按钮用扩展热区，不改变视觉大小） |
| 「判断结果怎么看」折叠入口 | 目标样式选择器写错（`.case-card__more summary` 但 class 就在 summary 上），既没有箭头也只有 21px 高 | 样式生效：28px 高 + 展开箭头 |
| 需求确认页两栏布局 | 左栏 10 条、右栏 1 条，右侧大片空白 | 改为一栏到底，阅读顺序不变 |

当前 5 个页面（工作台 / 项目管理 / 材料解析 / 需求确认 / 售前建议）结果均为空，控制台无报错。

## 7. 第三轮：判断表收敛为两列 + 首页动态默认 3 条

### 7.1 逐条判断表：5 列 → 2 列

| 列 | 处理 |
| --- | --- |
| 客户需求 | 保留（标题 + 描述 + 来源页码） |
| 匹配结果 | 并入「判断结论」列：状态徽标 |
| 产品能力 | 并入「判断结论」列：只留一句话结论 + 前置条件；完整产品资料仍在展开区 |
| 历史案例 | 从列里移走：列上只留「N 个案例」，案例名单放进展开区的「相关历史案例」 |
| 依据 | 并入「判断结论」列底部：`N 条依据 · N 个案例` + 展开箭头 |

配套改动：

- 去掉 `min-width: 1020px`（原先在窄屏必须横向滚动），改为 `table-layout: fixed` + 列宽 56% / 44%，单元格加 `overflow-wrap: anywhere` 防止长文件名撑破；
- 去掉大屏下「首列吸左」的样式（不再需要横向滚动）；
- ≤900px 仍然是卡片模式，只是标签从 5 个减到 2 个（客户需求 / 判断结论）。

实测：1512px（454/357）、1024px（510/401）两列正常，880px 起转卡片，三种宽度都没有横向滚动或溢出。

### 7.2 首页「最近动态」默认 3 条

超过 3 条时，区块标题右侧出现「展开全部 N 条」，点开后原地展开、再点「收起」回到 3 条。
这样首屏永远留给「分析新项目」，长历史不会把主操作挤到折叠线以下。

## 8. 第四轮：全站文案去重（产品视角）

把「用户此刻已经知道的信息，不要再说一遍」当成一条硬规则，逐条清理。举一个用户点出来的例子：`删除这份资料` → `删除`。

### 8.1 六条可复用的删除规则

| 规则 | 反例 | 改法 |
| --- | --- | --- |
| **动作名不带宾语**（上下文已经说明对象） | 删除这份材料 / 保存修正 / 打开项目 / 重新分析这个项目 / 重新提取项目要点 | 删除 / 保存 / 打开 / 重新分析 / 重新提取要点 |
| **提示消息不复述动作对象** | 材料已删除 / 需求已更新 / 项目要点已更新 / 已确认，这条需求会进入能力判断 | 已删除 / 已更新 / 已更新 / 已确认，将进入能力判断 |
| **正常状态不声明** | 材料栏常驻「全部已读取」 | 只在异常时说话：「2 份读取失败」「1 份读取中」 |
| **同一句话只说一次** | 进度条标题「正在判断需求能不能做」+ 步骤标签又是同一句；Agent 汇报里「读不出来的内容不会被引用」在理由与建议里各说一次；资料输入框的「交给 Fitwise」与首页主按钮同名 | 标题说过的不再作为步骤标签；理由只讲事实、建议只讲动作；输入框改为「存入材料」 |
| **分区标题说过的，不在条目上重复** | 「核心需求」每条都挂「客户明确需求」标签，「隐含需求」每条都挂「AI 推断」标签（11 条 = 11 个重复标签） | 标签删除，语义由分区标题 + 帮助气泡承担 |
| **紧凑位置用短标签** | 筛选器与徽标显示「信息不足，需要确认 0」 | 徽标/筛选器用短标签「待确认」，完整说法留在图例与下拉选项 |

### 8.2 顺带清掉的死文案

排查时发现三处「写了但从不渲染」的文案，一并删除（它们会误导后续维护）：

1. 首页分析流程里的 4 条阶段文案（`正在创建客户与项目` 等）——组件只把它当布尔开关，改为 `intakeRunning` 状态变量；
2. 项目列表 `focusOf()` 里的 6 条「AI 建议」——列表早就只渲染 `judgment`，改成只返回判断与色调；
3. 进度条第三个阶段「刷新页面 / 完成后你会直接看到结果」——刷新是自动的，这个阶段是假的，删掉后进度条变成真实的两步。

### 8.3 次要动作统一入口

需求卡上的「编辑 / 删除」两个文字链，与材料行、项目要点卡片统一收进右上角 `···` 菜单（保留「确认」作为唯一的主动作）。
全站次要操作现在只有一种形态，用户不用在两种模式之间切换。

## 9. 第五轮：风险按等级分区 + 项目信息前置

### 9.1 风险提示：按高 / 中 / 低分区，高风险默认展开

改动前：所有风险混在一条列表里，前 3 条铺开、其余塞进「查看其余 N 条风险」，用户看不出哪些是真正会卡住项目的。

| 区块 | 默认状态 | 展开后 |
| --- | --- | --- |
| 高风险 | **展开** | 完整卡片：标题 + 详情 + 建议应对 |
| 中风险 | 折叠 | 紧凑列表：标题 + 详情 |
| 低风险 | 折叠 | 紧凑列表：标题 + 详情 |

- 每个区块标题带数量（如「高风险 3 条」），区块右侧有展开箭头；
- 卡片里不再重复「高 / 中 / 低」徽标——分区标题已经说明了等级；
- 区块标题的「共 8 条」只在总标题出现一次，不在每个区块重复总数。

实测：高风险 3 条默认展开（3 张卡片），中风险 4 条、低风险 1 条折叠（折叠后仅 41px 高，不占版面），点击可随时展开收起。

### 9.2 项目信息移到三个功能之上

原来的顺序是「项目名 → 三个功能页签 → 项目信息」，等于让用户在切换功能之后才发现项目背景。
现在改成「项目名 → 项目信息 → 三个功能页签」：先看清这是什么项目、时间线与决策链，再进入具体功能，页签仍然贴着卡片底边。

## 10. 第六轮：风险与行动统一成同一套分组卡片

### 10.1 问题

风险提示原来是「3 张卡片 + 一条『查看其余 N 条风险』」的混排，卡片形态和右侧的行动建议完全不同：左边是带左侧色条的卡片墙，右边是带图标、计数、复制按钮的分组卡。同一屏里两套语言，看起来像两个产品拼在一起。

### 10.2 改法

风险提示直接复用行动建议的分组卡片（`.action-group`）：三个分区 = 三张卡，标题栏结构与行动建议完全一致（等级色图标 + 等级名 + 数量 + 折叠箭头）。

| | 默认状态 | 卡片内容 |
| --- | --- | --- |
| 高风险 | 展开 | 标题 + 详情 + 建议应对 |

## 12. 第八轮：上传入口搬进 Agent（2026-09-14）

### 12.1 判断标准：入口进 Agent，对象留中间页

**动作在对话里发起，对象留在页面上。** 上传、重新读取、发起分析属于动作，交给右侧 Agent；
材料行、项目要点、需求条、判断表属于对象，留在中间页。

反过来说：**需要横向对照的活儿不搬进对话流。** 「逐条确认 11 条需求」在 332px 宽的对话里
比现在的表格慢，所以对话只负责下指令（「确认高优先级那 3 条」），执行与结果仍留在中间页。

### 12.2 材料解析页：两个上传入口 → 0 个

| 位置 | 改动前 | 改动后 |
| --- | --- | --- |

| 保留 | 材料清单、读取状态、失败重试、删除、项目要点 | 不变（「重新提取要点」仍在 `···` 菜单里） |

### 12.3 Agent：从「问答框」变成「收件口 + 回执」

| 新增 | 说明 |
| --- | --- |
| 输入区「上传」 | label + file input，键盘可达；拖拽只是加速通道 |
| 整页拖拽投放 | 文件拖到页面任何位置都算交给 Agent，拖拽时整页出现虚线投放层 |

| 材料卡 | 对话里的一条回执：类型 + 文件名 + 状态 + 动作（查看原文 / 重新读取） |
| 拦掉浏览器默认行为 | 不拦 `dragover`，浏览器会直接打开被拖进来的文件 |

材料卡的边界（决定了它会不会变成第二个页面）：

- 只存 `material id`，状态从 `project.materials` 实时读 —— 卡片与材料行永远是同一份数据，不会出现两套进度；
- 不放原文、不放要点清单 —— 那是材料行与原文抽屉的事；
- 不放确认 / 编辑 / 忽略 —— 卡片是回执，不是操作台。

### 12.4 保持一致的细节

| 细节 | 做法 | 理由 |
| --- | --- | --- |
| 上传成功不弹 toast | 卡片本身就是回执，只在异常与判重时说话 | 「正常状态不声明」 |
| 判重按 `filename + size_bytes` | 重复拖入只提示，不生成第二条材料记录 | 同一份材料被引用两次会污染判断 |
| 读取中不给百分比 | 后端状态只有 `uploaded / parsing / parsed / failed`，所以给一条来回走的线 | 不假装有按页进度 |
| 窄屏上传后自动展开抽屉 | `≤1199px` 时 Agent 是底部抽屉，不展开用户看不到任何反应 | 上传必须有回执 |

### 12.5 顺手修的

| 问题 | 修法 |
| --- | --- |
| 1181–1199px 中间页右侧空 300px：`.workspace-grid` 还留着第二列，但 `.agent` 此时已经是 fixed 抽屉 | 媒体查询从 `max-width: 1180px` 改成 `1199px`，并删掉永远不会生效的 `.agent { position: static }` |

### 13.2 顺手补的

| 补的东西 | 理由 |
| --- | --- |
| 卡片加 `撤回` | 拖错文件不用等它读完再去材料行删 |
| `uploaded` 显示「已收到 · 排队中」 | 和 `parsing` 的「正在读取…」分开，一次拖 5 份时看得出哪些还没轮到 |

### 13.3 删材料的数据修复（后端）

改动前：`Requirement.source_material_id` 是 `ondelete="SET NULL"`，所以删掉材料后，它抽出来的需求与要点**全部留在项目里** —— 材料没了、依据也没了，需求还挂在清单上。

| 对象 | 处理 | 理由 |
| --- | --- | --- |
| 草稿需求（draft） | 随材料一起删 | 依据没了，AI 推断的草稿不该留在清单上 |
| 已确认需求（confirmed） | 保留（`source_material_id` 置空） | 人工基线；`source_material_name` 还在，出处说得清 |
| 项目要点：人工改过 / 忽略过 | 保留 | 与重新抽取的口径一致（edited / ignored 一律保留） |
| 项目要点：没动过的 | 删除 | 它们只指向已经不存在的材料 |
| 材料分片 | 级联删除 | 原文已不存在 |

删除确认的文案同步说清后果：「由它抽取的 3 条待确认需求会一起删除。已确认的 2 条需求会保留。」

回归脚本 `scripts/check_material_delete.py` 对**数据库副本**跑（自己复制到临时目录，并把 `storage_path` 指到临时路径，不会碰真实数据与真实上传文件），断言上面五条规则。实测：

```
before: material_exists=True  chunks=3  project_requirements=11  this_material_drafts=1  confirmed_by_name=10
after:  material_exists=False chunks=0  project_requirements=10  this_material_drafts=0  confirmed_by_name=10
RESULT: PASS
```

> 写断言时踩过一次自己的坑：第一次按 `source_material_id` 数「已确认需求还在不在」，删除后必然数到 0（被 FK 置空了），误报成「已确认需求被删」。**删除后仍然成立的证据是 `source_material_name`** —— 这点值得记住。

### 13.4 这一轮没做的

1. **拖拽悬停时报「将上传 3 份 · 共 12 MB」** —— `dragover` 阶段浏览器不给文件大小（`dataTransfer.files` 是空的），只能报个数；等和 parse job 一起做；
2. parse 登记成 job（真实「正在读第 3/12 页」）；
3. 同名材料作为新版本（`Material.version` 仍未使用）；
4. 失败原因归类说人话（现在仍是 TextIn 原始错误串截 60 字）。

> 验证状态：类型检查、生产构建、浏览器结构检查（右栏 332px、中间页单列、全页只有 Agent 里那 1 个 file input、控制台无 error/warning）都通过；

## 14. 第十轮：对话从「模板」换成「单步 Agent 路由」（2026-09-14）

### 14.1 改了什么

右侧 Agent 的对话原本是 6 条前端正则（材料 / 风险 / 案例 / 确认 / 需求 / 能力），命中不了就回「这个问题我答不了」。
现在换成一次真正的单步路由：

```
用户提问 → material_search 取证据（项目要点 + 材料原文）
        → 一次 chat_json：要么给带页码的回答，要么给出一个动作意图
        → 前端执行动作（走既有端点）或渲染回答 + 引用
```

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 检索 | `server/app/services/material_search.py` | 两路证据源：项目要点（标签「工期口径」这类能直接命中）与材料原文片段，都带页码 |
| 路由 | `server/app/services/agent_router.py` | 一次调用决定 answer / action；引用由命中生成；动作资格由项目状态把关 |
| 接口 | `server/app/routers/agent.py` | `POST /api/projects/{id}/agent/ask`，**只读**：不改任何数据 |
| 执行 | 前端调用既有端点 | `/requirements/extract`、`/matches/run`、`/solutions/generate`，权限与留痕仍只有一条路径 |

### 14.2 为什么检索要加「项目要点」这一路

实测发现：材料原文写的是「**1.4 项目周期**」，而用户问的是「工期是多久」—— 关键词对不上，纯原文检索召回为 0。
但 Agent 1 早就把这段摘成了带标签的要点「**工期口径**」，标签能命中，页码也在。

所以检索合并两路证据：要点负责答对问题，原文负责补细节。这一改让「工期是多久」从「材料里没有提到」（错）变成第 1 页引用（对）。

### 14.3 权限边界（这一轮就立住）

Agent 只能**提议**动作，能不能做由项目状态决定，不由模型决定：

| 动作 | 前置条件 | 不满足时 |
| --- | --- | --- |
| `run_full_analysis` | 至少 1 份材料读成功 | 「先上传材料我才能分析」 |
| `run_extraction` | 至少 1 份材料读成功 | 同上 |
| `run_matching` | 至少 1 条**已确认**需求 | 「还有 N 条需求等着你确认」 |
| `compose_solution` | 至少 1 条能力判断 | 「先做一轮判断」 |

模型说的动作也要过这道闸；引用同样只从检索命中里取，页码对不上就不给引用。

### 14.4 验收（可复现）

`scripts/check_agent_router.py`（对数据库副本跑，只读）实测：

| 问 | 结果 |
| --- | --- |
| 工期是多久？ | answer · 第 1 页引用 · 内容正确（4 个月） |
| 交付环境有什么要求？ | answer · 第 1、3 页引用 |
| 付款周期是多少？ | answer「材料里没有提到」· **不给引用**（材料里确实没有） |
| 重新跑一遍分析 | action · `run_full_analysis`（只提议，不执行） |
| 你好 | answer · 正常回应，不再说「材料里没有提到」 |

浏览器实测同样通过：提问 → 带页码回答 → 点引用打开「材料与依据」抽屉。

`scripts/check_material_search.py` 是配套的调参工具（看分片里有什么、一个问句命中哪几片）。

### 14.5 这一轮没做的

1. **动作执行路径没有在界面里实跑** —— 触发一次「重新跑一遍分析」会真的重写演示项目的需求与判断，所以只验证到「路由给出的动作正确」这一层（curl 实测）与类型层（构建通过）；
2. 多步串联、会话持久化、工具回执卡、审批卡：那是迁移路径的第 2、3 步；
3. 判断逐条串行调用、材料 digest 45k 字符上限：仍待第 4 步（检索升级）解决。

## 15. 第十一轮：会话持久化 + 状态机 + 工具回执卡（2026-09-15）

迁移路径的第 2 步，分两小步做，每小步都跑一遍原能力回归。

### 15.1 2a · 会话与消息持久化

| 层 | 文件 | 做了什么 |
| --- | --- | --- |
| 表 | `models.py` · `AgentMessage` | `role`（user / agent / tool）× `kind`（text / material / job）+ `data`；**只存 material_id / job_id，状态仍实时读** |
| 服务 | `services/conversation.py` | append / recent / update，文本截断与条数上限都在这一层 |
| 接口 | `routers/agent.py` | `GET/POST /agent/messages`、`PATCH /api/agent/messages/{id}`、`DELETE /agent/messages`；`/agent/ask` 现在会把提问与回答一起落库 |
| 前端 | `AgentPanel.tsx` | 挂载时读历史；材料卡与工具卡都落库；卡片 key 用 `srv-{id}` / `local-{n}` 区分，不会撞号 |

失败也要留痕：不支持格式、上传失败都会落成一张 `status=failed` 的工具卡（刷新后仍看得到，但没有原文件可重试）。

### 15.2 2b · 状态机与多步执行

`next_step(state)` 是**唯一**的"下一步"来源：

```
没有材料 → 重试失败件 → 整理需求 → 确认需求（人工闸门）→ 能力判断 → 生成售前建议 → 无
```

- `build_plan(state)` 按状态机往下**模拟**，遇到闸门就停 —— 实测：从零开始只跑 `run_extraction`，然后停在「确认这 1 条需求」；
- `GET /agent/state` 把 `state` 与 `next_step` 暴露给界面；
- 界面上的「下一步：做能力判断」提示只在**能自动做完**时出现（要人做的留给报告区的「下一步」，不重复）；
- 说「从头跑一遍完整流程」→ 按计划串多步，每步一张工具回执卡，跑完提示自动消失。

### 15.3 验收（每小步都跑）

| 检查 | 命令 | 结果 |
| --- | --- | --- |
| 原能力回归 | `scripts/regression_check.py` | PASS（上传 → 解析 → 抽取 16 条 → 确认 → 判断 16 条 → 建议 → 行动项，全程沙箱） |
| 对话与回执卡 | `scripts/regression_check.py --with-agent` | PASS（提问落库、引用可读回、回执卡可建可更新） |
| 状态机与路由 | `scripts/check_agent_router.py` | PASS（5 个状态 + 计划停在闸门 + 5 个问答） |
| 浏览器实测 | `scripts/uitest_sandbox.py` | 「下一步：做能力判断」→ 两步计划 → 两张卡 running→done → 刷新后卡片仍在、提示消失 |

配套工具：`regression_check.py`（复制库 → 8010 起后端 → 跑 e2e → 删临时目录，零残留）、
`uitest_sandbox.py`（复制库并把项目重置到「还没判断」→ 8010 后端 + 5199 前端）、
`check_agent_conversation.py`；`e2e_smoke.py` 支持 `FITWISE_BASE` 指向任意实例。

### 15.4 这一轮的三个坑（都值得记）

1. **`uvicorn --reload` 在这台机器上会卡住**：日志停在 `WatchFiles detected changes ... Reloading...`，worker 不重启、新路由 404。
   改成不带 `--reload` 启动（与原来一致），改完后端手动重启；重启时 `uvicorn.log` / `uvicorn.err.log` 会被重定向覆盖。
2. **清理不能按时间批量杀进程**：用「最近 8 分钟启动的 python」清沙箱，把线上后端一起杀了 —— 清理要按端口或明确 PID。
3. **前端 esbuild 在沙箱里读不到项目文件**：起 5199 那套 UI 必须提权，和 `vite build` 要提权是同一个原因。

- 计划执行中断后不会自动续跑（本次不做，属第 3 步范围）。

## 16. 第十二轮：右侧定为核心交互面 + 审批卡（2026-09-15）

### 16.1 右侧不再随中间页变

需求原话：**右侧是核心交互面，无论中间界面切到哪里，右侧内容都一致。**

| 改动 | 之前 | 现在 |
| --- | --- | --- |
| 右侧汇报 | 按模块三套（材料状态 / 需求状态 / 当前判断），连 CTA 都不同 | **一张项目状态卡**：一句结论 + 三条理由 + 三个功能的进度 + 下一步 |

## 17. 第十三轮：删掉「项目信息」（时间线 + 决策链）

### 17.1 为什么删

先说清这两块的数据来源 —— 也是它们该走的理由：

| 块 | 来源 | 谁写 | AI 参与吗 |
| --- | --- | --- | --- |
| 项目时间线 | `activities` 表，前端按 7 类事件白名单过滤后取最近 8 条 | 后端在固定节点调 `log_activity` | 不参与，只是日志 |
| 决策链 | `contacts` 表（**按客户存，不按项目**） | 种子数据 + 客户档案页手工添加 | **既不读也不写**，不参与任何判断 |

三条删除理由：

1. **不是三大功能的产物**：一个不参与 AI 的模块，在"聚焦三大核心功能"的 demo 里是背景噪音；
2. **决策链在演示里会露怯**：演示客户 0 位联系人 → 显示「未识别到决策人」，而同一页的材料解析里可能就有 AI 摘出来的「决策链」要点（两个同名不同源的东西摆在一起）；
3. **时间线的价值已被对话取代**：这一轮之后，「AI 做过什么、谁确认的、什么时候」都在对话的回执卡与批准留痕里，而且是完整的；时间线是**过滤过的子集**（覆写判断、更新要点这类动作不显示），留着反而让人怀疑"是不是没留痕"。

### 17.2 删了什么

- `ProjectContextBar.tsx`：`<details className="project-info">` 整块、`TIMELINE_TYPES` 映射、`contacts` 与 `timeline` 两处派生数据；
- `workspace.css`：`.project-info`（5 条）、`.node-list`（5 条）、上一轮留下的死样式 `.context-bar__sub`。
  CSS 从 125.2 kB 降到 123.9 kB。

中间页顶部现在只剩：**项目名 + 材料与依据 + 三个功能页签**。

### 17.3 能力去哪了（都没丢）

| 原来在这里 | 现在在哪 |
| --- | --- |
| 客户联系人 / 决策链 | 客户档案页（联系人 + 影响力，本来就是它的家） |
| 项目历史 / 留痕 | 工作台的最近动态 + 对话里的回执卡与批准记录 |
| 项目要点里的「决策链」事实 | 材料解析 → 项目要点（带来源页码，AI 抽出来的那条） |

数据一行没删：`contacts` 与 `activities` 两张表照旧。**要恢复只是前端的事** ——
把上面 17.2 列的四样东西抄回来即可（活动记录仍随项目详情返回，工作台的最近动态还在用）。

### 17.4 以后真要做"AI 识别决策人"该怎么做

不要复活这份手工列表，而是把材料里那条「决策链」要点做实：让 Agent 1 在抽取时把决策人**结构化**（姓名 / 职务 / 角色 / 来源页码），
落在项目要点里，能点回原文；客户档案的联系人保持人工维护、作为对照。这样"AI 找到的"和"人记录的"分得清，也不会互相打架。

## 18. 第十四轮：售前建议页重排 + 风险/行动的依据链（2026-09-15）

### 18.1 问题：折的是主产物，展开的是派生物

「逐条判断」是这一页最大的产物，却被塞在页尾的 `<details className="legacy-details">` 里；
风险与行动是它的派生物，反倒是展开的。折叠条还叫「逐条判断依据」，点开却先看到三个视角切换 —— 落差在这儿。

### 18.2 版面按信息流重排

```
结论条：谨慎推进：有条件地继续 + 复制建议
        ├ 需求判断：10 条里 3 条完全支持、5 条要先确认前提、2 条暂不支持   → 跳
        ├ 风险：8 条，其中 3 条高影响                                        → 跳
        └ 下一步：向客户发出确认清单，收齐页型占比与票据清单…                → 跳
              ↓ 凭什么这么说 ↓
能不能做（10 条需求）：四个计数做成可点筛选；默认只列「需要注意的」（暂不支持 + 待确认 = 2 条）
                       下面一行：其余 8 条：3 条完全支持、5 条要先确认前提，展开看全部
              ↓ 所以接下来 ↓
风险提示（每条挂着它依据的判断与证据）
行动建议（三组，销售组每条同样挂着依据）
```

- 三句概括**由数据拼装**（不用再调一次模型），并且各自是一个跳转 —— 它同时是这一页的目录；
- 「需求分析」改叫**能不能做**，不跟隔壁「需求确认」页抢名字；
- 删掉 `.legacy-details` 那层包装与它的 6 条样式；`MatchingModule` 作为 slot 传进 `JudgementPage`（结论文案要用它的计数）。

### 18.3 依据链：风险与行动现在能回指了

改动前：`SOLUTION_SCHEMA` 里 `steps` 有 `based_on`，`risks` 与 `next_actions` 没有 —— 所以从生成那一刻就没有 id 可存。

| 层 | 改动 |
| --- | --- |
| 提示词 | 匹配结果带编号（`1. 需求标题：结论｜缺口｜待确认`）；要求 risks / next_actions 每条写 `based_on: [编号]` |
| 落库 | `_attach_requirement_ids()`：编号 → 需求 id（**编号优先，标题只认完全同名**）；对不上就丢掉 |
| 读取 | `solution_out(solution, db)` 用 `requirement_ids` 现查判断与证据，拼成 `basis` —— 存 id、读时解析，重新跑判断后依据不会过期 |
| 界面 | `BasisList`：先给「哪条需求」，再给证据。客户材料那侧能打开原文抽屉；能力库 / 案例只给「文档名 + 页码 + 摘录」（知识库没有全文浏览，不假装能点开） |

**踩过的坑**：第一版按标题做"包含"匹配，8 条风险里有 4 条多挂了相邻需求（把「各类票据日均处理量」错配到「各类票据日均处理量与字段数」）。
改成让模型回**编号**之后，8/8 条都能回指、7 条完全准确（剩下 1 条多挂了一个"等保三级"，可接受）。
结论：**让模型选编号、后端校验**，比让它写标题再模糊匹配可靠得多。

### 18.4 验收

| 检查 | 结果 |
| --- | --- |
| 原能力回归 `regression_check.py` | PASS；新增断言「风险依据链 8/8 条能回指」 |
| 线上实测（项目 #1 生成建议 v3） | 每条风险都挂上判断与证据，例：工期风险 → 交付服务标准 P8/P12 + 客户 RFP P1（客户侧与能力库侧同时给出） |
| 浏览器实测 | 版面顺序 = 结论条 → 凭什么 → 能不能做 → 所以 → 风险 → 行动；默认只列 2 条需注意的判断；12 处依据可点；`.legacy-details` 已消失 |

### 18.5 还没做

1. 风险 / 行动的**直接原文跳转**只做到两级（先到判断、再点页码）—— 想要一级直达，需要把证据 id 也存进 solution；
2. 判断表默认筛选目前是固定规则（暂不支持 + 待确认），没有记忆用户上次的选择；
3. 匹配度 / 赢单可能性仍留在结论条右侧（按提案本可降级进「能不能做」的概括行，先保留观察）。

## 19. 第十五轮：材料一句话总结 + 要点按内容分区（2026-09-15）

### 19.1 材料清单要有"这份材料写了什么"

原来材料行只有「招标 / 需求文件 · 文件名 · 3 页 · 已读取」——知道是什么文件，不知道写了什么。

| 层 | 改动 |
| --- | --- |
| 产出 | `REQUIREMENT_SCHEMA` 加 `material_summaries[{material_name, summary}]`，让 Agent 1 在抽需求时**顺带**写一句（同一次调用，不加成本、不多花钱） |

| 界面 | 材料行在状态后面多一行：这份材料整体写了什么。实测样例：<br>「XX城市商业银行智能票据与档案处理平台的招标需求书，写明工期、规模、部署、合规、识别能力、接口与验收要求。」 |

→  交付环境 2  →  预算 n  →  决策链 n  →  其他要点 n

- 分区标题带数量，条目上**不再重复标签**（`highlight-item__label` 已从界面上消失）；
- 没见过的标签归入「其他要点」，不让它静默消失；
- 每条要点原有的「来源页码 / 编辑 / 忽略」都没动；「恢复已忽略的 N 条」仍在区块右上角。

## 20. 第十六轮：三个功能页统一骨架（2026-09-15）

### 20.1 问题

三页的骨架各不相同：售前建议是「结论条 + 可点概括 + 数字 + 主动作」，材料解析和需求确认却是

### 20.2 统一成一句话：结论条 + 分区

抽出共用组件 `src/components/project/SummaryBar.tsx`，三页共用：

```
① 结论条：一句结论 + 依据行 + 三句概括（各自可点跳转）+ 两个数字 + 主动作 [+ 次要动作]
② 分区：h3 + 数量徽标，条目结构统一（标题 → 详情 → 元信息 → 依据 → 次要动作 ···）
```

| 结论句 | 1 份材料都读完了，摘出 7 条项目要点 | 10 条已确认，1 条等你确认 | 谨慎推进：有条件地继续 |
| 三句概括 | 材料 / 项目要点 / 下一步(跳需求页) | 需求 / 待确认 / 要问客户 | 需求判断 / 风险 / 下一步 |
| 两个数字 | 客户材料 · 原文页数 | 已确认 · 待确认 | 能力匹配度 · 赢单可能性 |
| 主动作 | 去需求确认（未提取要点时＝提取要点） | 全部确认（N） | 重新判断 |
| 分区 | 客户材料 N → 项目要点 N（内部按标签二级分类） | 核心需求 N → 隐含需求 N → 待确认问题 N | 能不能做 N 条 → 风险提示 N → 行动建议 N |

配套调整：

- **需求确认的「还差什么」下沉**：原来挂在顶部（只列最关键 2 条），现在是一句概括 + 第三个分区「待确认问题（N）」列全量；
- **「全部确认」上移到结论条**（原先在「隐含需求」分区头，两处都有按钮就是重复）；
- **材料解析的主按钮是「去需求确认」**，上传入口留在右侧 Agent；「重新提取要点」作为次要动作；
- 材料清单也套上同一个分区壳（标题「客户材料 N」），它和「项目要点」才是并列的两块。

## 21. 需求确认页加「查看建议」入口（2026-09-15）

三块内容是一条链：材料 → 需求 → 建议。前两页各自已有"去下一页"的动作（材料解析 = 去需求确认），
需求确认页缺一个到售前建议的入口 —— 补上，并按"主动作 = 这一页的下一步"放置：

| 项目状态 | 主动作 | 次要动作 |
| --- | --- | --- |

## 28. 第二十二轮：三个功能页的按钮规则与用词对齐（2026-09-15）

### 28.1 按钮规则：左边永远是本页功能，右边永远是去下一段

三个功能页共用同一个结论条，按钮槽位是固定的：

| 槽位 | 内容 | 例子 |
| --- | --- | --- |
| 左（主动作） | **本页功能** | 材料解析「重新提取要点」/ 需求确认「全部确认（N）」/ 售前建议「重新判断」 |
| 右（ghost） | **去下一段** | 去需求确认 / 查看建议 / 去行动建议 |

需求确认页原先在「没有待确认」时会把「查看建议」放到左侧主动作上 —— 同一个按钮，位置一会儿在这儿、
一会儿在那儿，用户就得每次重新找。现在左边只放本页功能，没有待确认时左侧就空着，右侧固定「查看建议」。

### 28.2 用词：一个词只说一件事

原来「待确认」在同一页里说了两件事：

- 概括行「待确认」= AI 推断出来的**需求**，等你点确认；
- 分区「待确认问题」= 材料没写清、要**问清楚的问题**（里面既有问客户的，也有内部先确认的）。

改法：分区与概括行统一叫「**待澄清**」，并且把问谁分清楚。

```
待澄清   7 处（问客户 6 · 内部 1，1 处影响判断）      ← 概括行
待澄清问题 7                                          ← 分区标题
  [客户] 现有影像平台由第三方提供，具体对接方式…       ← 标签就是「问谁」
  [内部] 本项目预算区间和评标关注点是什么？
```

「待确认」从此只指 AI 推断的需求（`N 条 AI 推断等你确认`、状态徽标「待确认」），一个词只有一个意思。

## 29. 第二十三轮：风险从「一个板块」降级成「一个视图」（2026-09-15）

### 29.1 判断：板块该退休了

形态 4 之后，风险正文已经长在判断条目里，板块剩下的只是一份"高影响标题索引"——
同一批标题在页面上出现第二遍。用户要的不是第二个清单，而是**能按风险看**的视图。

### 29.2 改法与口径

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 筛选栏 | `全部 10` + 四个判断档 | 再补一条分隔线与 `高风险 5 / 中风险 3 / 低风险 1` |
| 风险正文 | 高风险默认展开，中低风险要点标记才展开 | 选中任一风险档 → **该档条目的风险正文全部展开**，一眼看完 |
| 结论条「风险」那句 | 跳到风险板块（板块删了就是死链接） | 点一下 = 切到高风险视图并滚到「能不能做」 |

两条口径写死在代码里，避免以后又对不上：

1. **数字 = 行数**：筛选栏上的 N 就是点下去能看到的条目数（同一条需求可能同时挂在两个等级下，
   因为一条需求可以对应多条风险）；这个口径由 `requirementIdsOfLevel()` 统一算。
2. **两套筛选互斥**：判断档与风险档二选一，不做叠加 —— 叠起来会出现"部分支持 + 高风险 = 2 条"
   这种需要解释的空态。0 条的那一档直接禁用，同一排里"能不能点"的规则保持一致。

MatchingTab 与 MatchingModule 共用，不再各写一份 `RISK_ORDER`。

### 40.2 修法（按 MVP 原则：不为了让结论好看，而是让演示数据和剧本对齐）

2. `scripts/demo_reset.py` 新增 `--reseed-kb`：种子文件改了之后重建知识库 ——
   `seed_knowledge()` 只在库为空时灌数据，不重建的话演示口径还是旧的；
3. `scripts/demo_check.py` 加护栏：**gap 信号必须存在**，且它的 tags **不许用泛标签**
   （archive / pdf / scanned / document-parse …），否则演示前就报出来。

### 40.3 中途踩的两个坑（都记下来）

**坑 1：gap 信号挂了泛标签，把所有需求一起拉低。**
第一版我把 gap 的 tags 写成 `["archive","drawing","large-format","scan"]`。检索是**按标签命中**的，
`archive` 是每条档案馆需求都会带的标签 → 所有需求都命中这条 gap → 规则层把 16 条里 11 条判成"暂不支持"，
连"馆内内网全离线部署"这种明显能做的也变成做不了。

教训：**约束信号的标签必须窄**（`large-format`、`special-ticket`、`handwriting` 这种只对应一类要求的），
不能是领域级标签 —— 这就是第 3 条护栏要守的东西。同时给 `TAG_RULES` 补了 `large-format`（大幅面 / 工程图纸 / 图纸 / 蓝图），

**坑 2：改了后端代码没重启。**

## 33. 第二十七轮：取消「隐含需求」分区 + 抽取去重（2026-09-15）

### 33.1 判断：这个分区不该存在

原来需求确认页分「核心需求 / 隐含需求」两块，分法是**来源**（客户明说 vs AI 推断）。
但这个分法有两个毛病：

1. 决定"能不能拿去判断"的其实是**状态**（草稿 / 已进基线），不是来源。按来源分，用户会开始纠结
   "这条到底是谁说的"，而这跟下一步该干什么没关系；
2. 实测里它产出了重复项 —— 项目 #1 里：

```
核心需求（已确认）  REST接口与SDK对接，峰值≥200QPS      第 3 页 · 依据 4 条
隐含需求（待确认）  标准接口对接现有影像平台              第 3 页 · 依据 1 条
```

同一页、同一件事抽了两遍，唯一后果是需求总数虚高（11 vs 实际 10）＋多一个分区＋多一次"要不要确认"的决策。

### 33.2 前端：一份清单，只按状态区分

| 之前 | 现在 |
| --- | --- |
| 核心需求 N / 隐含需求 N 两个分区 | 一个分区「需求 11」，草稿排最前面、基线跟在后面 |
| 草稿靠分区标题表达 | 草稿在标题后带「待确认」徽标，点确认后**原地**变成基线，不跨分区搬家 |
| 结论条「待确认」指向隐含需求分区 | 指向第一条草稿（锚点 `requirements-draft`），没有草稿时指向整份清单 |

### 33.3 后端：去重必须看描述，不能只看标题

原来只有标题级去重（`_is_duplicate_title`，阈值 0.78）。用项目 #1 的真实数据量了一下：

| 这一对 | 标题相似度 | 描述相似度 |
| --- | --- | --- |
| 上面那两条重复项 | **0.24** | **0.85** |
| 项目里其他任意两条（55 组） | < 0.4 | < 0.45 |

结论很清楚：标题完全不同也可能是一件事，**描述才是判据**。改成 `_is_duplicate_requirement()`：
标题规则保留（相同 / 互相包含 / ≥0.78），再加一条 —— 两条描述都 ≥12 字且相似度 ≥0.72 就算重复。
阈值取 0.72 是因为实测有安全区（最近的干扰项只有 0.45）。

顺手补了一条同源原则：**找不到来源材料的需求不进清单**（和项目要点一致 —— 没有证据就不说），
日志里会打出"去重跳过 N 条，无来源丢弃 N 条"。

提示词也加了一句：同一件事分处不同段落/页码也合并成一条，不要拆成两条近义需求。

## 34. 第二十八轮：一个词只干一件事（MECE 用词收敛，2026-09-15）

### 34.1 病根：同一条信息在四个地方、四种切法

| 出现在哪 | 原来叫什么 | 原来按什么切 |
| --- | --- | --- |
| 需求确认页 | 待确认 | 状态（草稿 / 已确认） |
| 需求确认页 | 待澄清问题 | 影响判断 / 不影响（文案这么写，实际列了全部） |
| 判断条目里 | 需要确认 | 按需求切 |
| 售前建议 · 行动建议 | 向客户确认 / 向研发确认 | 按"问谁"切 |

而且四种切法之间没对齐：**建议页生成"向客户确认"时把 `open_questions` 不分 owner 全塞了进去**，

### 34.2 收敛原则：定义唯一，视图正交

- **对象只有三类**：材料事实 / 需求 / 问题（待澄清）；
- **其余都是视图**：判断四档 = 需求 × 证据的结果；风险 = 判断的后果；行动建议 = 问题按"问谁"分组的执行视图；待办 = 行动的分派副本；

| 1 | 需求确认 · 概括行第二句 | `待确认 1 条 AI 推断等你确认` | `草稿需求 1 条，确认后进基线`；行内徽标同步改成「草稿」 |

## 30. 第二十四轮：「待确认」改名「待补依据」（2026-09-15）

### 30.1 为什么改

判断结果第四档原来叫「待确认」。它的真实含义是**没有依据、先不给结论**（检索层一条证据都没命中），
而不是"结论已出、等人点头"。三个问题：

1. 名字说的是"动作"，另外三档（完全支持 / 部分支持 / 暂不支持）说的是"结论"，一排里读起来不平；
2. 容易理解成"AI 判完了等人复核"，因果反了；
3. 和需求确认页的「待确认」（AI 推断的需求等你点确认）撞词 —— 同一套界面里一个词两个意思。

改成「待补依据」：说的是这一档**缺什么**，动作自然指向"补依据 / 问客户"，也不再和需求确认页撞词。

### 30.2 一次改齐，不留两种叫法

| 位置 | 现在 |
| --- | --- |
| 短标签（筛选胶囊、条目状态徽标） | `待补依据` |
| 完整标签（判断结果说明、下拉选项） | `信息不足，待补依据` |
| 说明文案 | 客户材料或我们自己的资料里找不到足够依据，先不给结论 —— 补齐依据或问清客户，再下判断。 |
| 售前建议结论条 | `、N 条待补依据`；口径句改成「还没依据的条目先按「待补依据」对客沟通，不做正面承诺」 |

| 工作台图例 | 判断结果怎么看（完全支持 / 部分支持 / 暂不支持 / 待补依据） |

### 42.6 补充（同日）：列表顺序改成稳定顺序

「草稿在前、已确认在后」是第 33 轮按"先把没确认的处理掉"定的，实测下来有个副作用：
点「确认」之后那一条立刻被顶到列表最下方，人当场找不到自己刚点的那条 ——
尤其是「改一条、看一眼、再改下一条」的用法里，视线要重新找一遍。

改成**稳定顺序**：列表顺序 = 需求自己的次序（后端按抽取顺序返回），
确认只改卡片上的标签（草稿 → 基线）与结论，位置一点都不动；
「结论条 → 待确认」的锚点改挂在第一条**还没确认**的需求上（不再假定位次是第一条）。
材料页的「材料里的需求」同样只按抽取次序排。

### 42.7 补充（同日）：「需求判断」那一句从售前建议搬回需求确认

售前建议的结论条上原来有三句（需求判断 / 风险 / 下一步）。第一句是需求的统计，
和逐条结论一样属于需求侧 —— 留着它，售前建议页等于第二次回答"能不能做"，
而它给出的链接又是"去需求确认看"，等于用一句话换一次跳转。

现在：

| | 需求确认 | 售前建议 |
| --- | --- | --- |
| 结论条上的概括 | 需求 / **能力判断（分档分布）** / 待澄清（入口指向售前建议） | 风险 / 下一步（两句，都指向本页分区） |

分档分布只列**有的档**，顺序按"越靠前越需要人管"：
`待补依据 1 · 暂不支持 2 · 部分支持 9 · 完全支持 1`（全是完全支持时就只显示 `完全支持 13`）。
这样统计和它统计的那批卡片在同一页，点「能力判断」直接滚到清单；售前建议页不再重复报一遍。

## 44. 第三十八轮：优先级有口径了 —— 提示词 + 越界检查 + 人工改档 + 按档排序（2026-09-17）

### 44.1 问题：P0 是模型随口标的，而且人人 P0

优先级只有一个 schema 字段（`"priority": "high|medium|low"`），提示词里**没有一个字解释三档是什么**，
落库时 `priority=str(item.get("priority") or "medium")` 也不做校验。实测分布：

| 项目 | 需求 | 标成 P0 的 |
| --- | --- | --- |
| 演示项目 | 13 条 | **11 条（85%）** |
| 项目 #2 | 15 条 | **13 条（87%）** |

一个 85% 条目都有的标签不再传达信息 —— 它变成了"这条挺重要"的语气词，而不是排序。

### 44.2 三处改动

| 层 | 改法 |
| --- | --- |
| 提示词（给口径） | 抽取要求新增 2.1 条：P0 = 客户写了硬性口径（必须 / 不得 / 不允许 / 不低于 / 不少于 / 应在…内）或带数字门槛的验收指标，做不到就交付不了；P1 = 影响方案、报价、工期的关键条件；P2 = 加分项与可选范围。并明确"标 P0 时 source_excerpt 里必须能看到那句硬性表述"。`PROMPT_SET_VERSION` 从 `2026-09-16.1` 升到 `2026-09-17.1` |
| 规则层（越界检查） | `agents.guard_priority()`：标 high 的条目，在**它自己的**标题 / 描述 / 原文片段里找硬性表述，找不到就降一档。降级条数与"认不出的值"条数进 job result（`priority_downgraded` / `priority_unrecognized`）与日志 |
| 落库（白名单） | `agents.normalize_priority()`：high/medium/low 之外的值（高 / P0 / 紧急…）统一收敛，别名认得出就按别名，认不出归 medium 并计数 |

闸门只看这条需求自己的原文，**不看整页** —— 之前试过把整页正文一起丢进去检查，
结果是"同一页只要有一句必须，这页上的需求就都能挂 P0"，闸门等于没有。

### 44.3 人工改档 + 按档排序

- 需求卡左侧的 P0/P1/P2 胶囊**本身就是入口**：点一下展开 `P0 高优先级 / P1 中优先级 / P2 低优先级`，
  选中即改（`PATCH /api/requirements/{id}`），改完给一句提示"列表已按新顺序排列"，因为卡片会移动到新位置。
  人工改过优先级算"已人工修改"（重跑抽取时不会被覆盖）。

## 45. 第三十九轮：确认挪到材料页、需求确认改名能力匹配（2026-09-17）

### 45.1 一句话

**材料页回答"客户要什么、我认不认"，能力匹配页回答"认了之后我们能不能做"。**

原来的分工是拧着的：材料页只读、需求确认页又确认又出结论 —— 而"这条到底对不对"要看客户原文，
原文偏偏在材料页那一边。确认搬过去之后，确认时看的证据就在同一张卡下面。

### 45.2 逐页改动

| 页 | 之前 | 现在 |
| --- | --- | --- |
| 材料解析 · 项目需求 | 只读事实留档（草稿 / 已确认标记 + 页码 + ···） | **可确认**：每条卡片下面直接摆**客户原文那一句**（`source.excerpt`，接口里本来就有、之前一直没渲染）；草稿有 `确认`（= 进基线 + 立刻匹配）；`···` 里「改写 / 删除」；已确认的标「已确认」。结论条主按钮 `全部确认（N）`，次要 `去能力匹配` |
| 需求确认 → **能力匹配** | 列全部需求（草稿 + 已确认），点确认出结论 | **只列已进基线的需求**：结论、风险、依据在卡上（依据可就地展开、人工覆写仍在这里）；页首两排筛选胶囊：结论四档 + 风险三级；没有"确认"动作（那一层在材料页）。tab 名字改成「能力匹配」，徽标数已确认条数 |
| 售前建议 | 不变 | 空态与「去下一页」的措辞跟着改（去材料解析确认 / 去能力匹配补判断） |

### 45.3 为什么"原文那一句"是这一步的前提

确认要判断的是"AI 改写的这句，算不算客户说的"。只给页码的话，用户得点开抽屉、翻到那一页、
在整页文字里找那句话 —— 13 条需求就是 13 次。而那句原文在抽取时就摘好存进库了
（`source.excerpt`），接口一直在返回，前端一次都没渲染。现在摆在卡片上：

```
P0  内网私有化全离线部署                      草稿
    平台要装在档案馆自己机房的内部网络里，全程离线运行…        ← AI 改写
    ┃「平台须在我馆机房内网私有化部署，全离线运行，不得向馆外
    ┃  传输任何档案影像与识别结果，不得使用公有云服务。」
    ┃  — 1-XX市档案馆数字化平台招标需求书.pdf · 第 2 页        ← 客户原文
    依据 5 条 · 第 2 页        [确认]  ···
```

页码链接照旧保留（想看上下文还是能点进去），引文只是省掉"要不要点开"这一步。

### 45.5 顺带定下的三条规矩

1. **未确认的永远是草稿**：服务端闸门没变（`_run_matching` 只取 `status == "confirmed"`），界面上草稿也只剩在材料页。
2. **改写只对草稿开放**：确认之前改措辞（`···` → 改写）；确认之后再改内容走能力匹配页的「编辑」，那条路径会自动重跑这一条判断。
3. **两个列表都按优先级排**：P0 → P1 → P2，同档保持抽取次序；材料页与能力匹配页看到的顺序一致。

### 45.6 顺带：售前建议的「下一步」改成"先办哪一件、谁办、什么时候"

售前建议的结论条一直是三句（风险 / 待澄清 / 下一步），但「下一步」那句原来是把
`next_actions` 的第一条整句塞进去、截到 30 字，结果是：**和「要同步销售」的第一条完全重复**，
而且取的是"模型写的第一条"，不是"最该先做的"（`priority` 与 `due` 一个字都没用上）。

现在：

- 「要同步销售」按 **优先级 → 截止日期** 排序（`domain/actions.ts` 的 `byPriorityThenDue`），
  顺带把那张卡的列表也排好 —— 最该先做的排最前；
- 结论条那一句取排序后的第一条，只留动作的**第一个短句**，后面跟责任人与日期：
  `下一步：向客户发确认清单（售前负责人 · 06-30）`（30 字的概括行里放得下，悬停有完整原文）；
- 那一条动作挂上 `id="next-action"`，点「下一步」直接落到它身上 ——
  「待澄清」仍然指向整个「要问谁」分区：两句回答的是两个问题（还剩多少 / 先办哪件）。
