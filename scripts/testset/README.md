# 回归题库（效果评测用）

`scripts/regression_check.py` 回答的是「链路有没有坏」；这个目录回答的是「效果好不好」。
材料是固定的，所以抽全率、越界率、证据覆盖才能复现 —— 和上一版比才有意义。

## 怎么跑

```bash
# 生成/重建材料（改了内容再跑一次）
.venv\Scripts\python.exe scripts\make_testset_materials.py

# 在回归沙箱里跑题库（推荐；不碰演示数据）
$env:FITWISE_SANDBOX_PORT="8023"; .venv\Scripts\python.exe scripts\regression_check.py --testset

# 只跑其中几份（已经在跑沙箱时）
$env:FITWISE_BASE="http://127.0.0.1:8023"; .venv\Scripts\python.exe scripts\check_testset.py --only 01,05

# 确认这套评测能判红（故意把答题卡改坏，预期出现红叉）
.venv\Scripts\python.exe scripts\check_testset.py --only 01 --verify-red
```

脚本会给每份材料建一个独立项目、走完整链路（上传 → 解析 → 抽需求 → 确认 → 能力判断），
再对着 `expected.json` 算四个数：抽全率（阈值 80%）、越界率（必须 0）、证据覆盖（必须 100%）、
需求条数是否落在答题卡给的区间内。

它默认拒绝对着 8000 的实例跑（会往库里建项目）—— 要在演示实例上跑得显式加 `--allow-prod`。

## 材料清单

| 文件 | 考什么 | 期望 |
| --- | --- | --- |
| 01-招标需求书.pdf | 长材料、关键约束埋在第 8 节、表格里的规模指标 | 该读出来的都读出来；大幅面图纸必须命中能力缺口 |
| 02-答疑与补充通知.pdf | 与 01 口径冲突（工期 6 个月 → 4 个月）、补充清单 | 冲突能被抓到并转成待确认 |
| 03-客户往来邮件.txt | 无页码材料、寒暄里夹一条真变更 | 抽出变更，不把闲聊当需求（用条数上限兜噪音） |
| 04-扫描件.pdf | 图片型 PDF、没有文字层 | 读得出来算过；读不出来必须明确失败 |
| 05-超范围需求清单.pdf | 五条硬要求全部超出能力边界 | 越界率必须为 0（一条都不许判成完全支持） |
| 06-损坏文件.pdf | 故意损坏的文件 | 明确失败 + 成因码，且不产出需求 |

## 怎么加一份真实材料

1. 把文件放进这个目录（命名沿用 `NN-说明.pdf`，编号往后排）；
2. 在 `expected.json` 的 `materials` 里加一项，字段含义：

   | 字段 | 说明 |
   | --- | --- |
   | `file` | 文件名 |
   | `project_name` | 评测时自动建的项目名（建议带编号，方便回溯） |
   | `expect_parse` | `parsed` / `failed` / `parsed|failed`（读不出来也算过的，用最后一种） |
   | `min_requirements` / `max_requirements` | 需求条数的合理区间，用来兜住"抽出一堆噪音" |
   | `must_extract` | 必须被读出来的关键词；命中范围是「需求 + 项目要点」，落成哪一类都算 |
   | `must_not_full_support` | 不该判成「完全支持」的关键词（越界率就是这么算的） |
   | `notes` | 这份材料要验证什么，写给下次改的人看 |

3. 先人工读一遍材料，把"真正的要求"数出来填进区间 —— **答题卡是人工写的，不能让 AI 生成**，
   否则评测就变成"AI 给自己打分"。

## 和真实材料的差距

这里的材料是合成的（除了你自己放进去的真实文件）：能稳定复现，能验埋得深、口径冲突、
无文字层、损坏文件这些情况，但**不能替代真实客户材料带来的意外**。
真要做"交付后会收到大量意外输入"这件事，就往这个目录里持续加真实脱敏材料。
